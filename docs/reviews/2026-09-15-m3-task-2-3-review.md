## The SHIFT_RIGHT / `push_thresh` conclusion

**The controller's suspicion is correct: with `SHIFT_RIGHT` and `push_thresh=24`
the 24 valid bits land in word bits 31:8, not 23:0, so the RP2040 profile's
`flags=0, samples_per_word=2, sample_bits=12` header describes a layout the
hardware never produces.** The RP2350 8×4 path is unaffected.

Reasoning, from the ISR semantics (RP2040 datasheet §3.4.4 `IN` / §3.5.4
autopush; "when `IN_SHIFTDIR` is right, the ISR shifts right and data enters from
the left"):

```
IN PINS,12 (sample s0):  ISR = (ISR >> 12) | (s0 << 20)     ->  0x ABC0_0000
IN PINS,12 (sample s1):  ISR = (ISR >> 12) | (s1 << 20)     ->  0x 123A_BC00
shift counter == 24 == push_thresh  ->  autopush the WHOLE 32-bit ISR
```

With `s0 = 0xABC`, `s1 = 0x123` the pushed word is `0x123ABC00`:

* actual: `s0 = (w >> 8) & 0xFFF = 0xABC`, `s1 = (w >> 20) & 0xFFF = 0x123`
* what `vgacap.stream.unpack_words()` reads with `flags=0, spw=2, bits=12`:
  `s0 = w & 0xFFF = 0xC00`, `s1 = (w >> 12) & 0xFFF = 0x3AB` — garbage.

The push is always 32 bits wide; only the *shift counter* is compared to the
threshold. Shifting right, the first sample is the one pushed furthest toward
bit 0, so the pair is right-aligned only when the threshold is 32. That is why
the RP2350 8-bit×4 case (threshold 32) is correct and the RP2040 12-bit×2 case
is not. No `flags` value can express it either: `FLAG_FIRST_SAMPLE_MSB` only
reverses the slot order within the word, it cannot shift the field by 8.

**Recommended fix (minimal, keeps SHIFT_RIGHT and the existing header):** pad the
ISR to a full word and push at 32.

```python
PAD = 32 - IN_COUNT * SAMPLES_PER_WORD        # 8 on RP2040, 0 on RP2350
@rp2.asm_pio(..., push_thresh=32, ...)
def sampler():
    wrap_target()
    wait(1, gpio, clk); wait(0, gpio, clk)
    in_(pins, in_count)
    wait(1, gpio, clk); wait(0, gpio, clk)
    in_(pins, in_count)
    in_(null, pad)          # only when pad != 0
    wrap()
```

`(0x123ABC00 >> 8) = 0x00123ABC` → `s0 = 0xABC` at bits 11:0, `s1 = 0x123` at
bits 23:12, bits 31:24 zero — exactly the brief's stated layout and exactly what
`unpack_words()` decodes. Cost: one extra instruction and one PIO cycle per word
(the loop is clock-bound, not instruction-bound), and 4 instructions total for
the unrolled form. `BoardProfile.push_thresh` then becomes 32 for both profiles
and the profile needs a `pad_bits`/`word_bits` notion instead — worth the
controller's ruling, since the brief explicitly says "24 for RP2040_TT06".

**Alternative (no extra instruction):** `in_shiftdir=SHIFT_LEFT` with
`push_thresh=24`. Data then enters at the LSB end: `s0` at bits 23:12, `s1` at
11:0 — which is precisely `FLAG_FIRST_SAMPLE_MSB` with `spw=2`, and likewise
correct for 8×4. It requires setting `flags=FLAG_FIRST_SAMPLE_MSB` in both board
profiles (a Task-1 file) and contradicts the brief's `SHIFT_RIGHT`.

Either way, a test must assert the *decoded* layout, not the decorator text.

## Findings

### Critical

**C1. CFG-derived constants are invisible inside the `@rp2.asm_pio` bodies — the
script dies with `NameError` the first time it runs on a board.**
`python/ttcap/mp/capture_rp2.py:147-173` (both `sampler` variants; the comment at
`:142-144` asserts the opposite).

MicroPython's `asm_pio` decorator does not merely inject the instruction
mnemonics — it **replaces the decorated function's globals**. From
`ports/rp2/modules/rp2.py` (v1.22, v1.24; master is the same with a `try/finally`):

```python
def dec(f):
    ...
    old_gl = f.__globals__.copy()
    f.__globals__.clear()
    f.__globals__.update(gl)      # gl == _pio_funcs + the emitter methods only
    emit.start_pass(0); f()
    emit.start_pass(1); f()
    f.__globals__.clear(); f.__globals__.update(old_gl)
```

`_pio_funcs` contains only `gpio`, `pins`, `x`, `y`, `null`, … plus the emitter
methods. `CLK_PIO_INDEX` and `IN_COUNT` are module globals, compile to
`LOAD_GLOBAL`, and are gone for the duration of the two assembly passes. (The
decorator *arguments* — `push_thresh=PUSH_THRESH`, `rp2.PIO.SHIFT_RIGHT` — are
evaluated before `dec` runs, so those are fine; it is only the instruction
operands that break.) This is why MicroPython PIO programs conventionally use
`micropython.const()`, which the compiler inlines — and `const()` cannot help
here because the values come from a runtime dict.

Reproduced in CPython by emulating the same globals swap:
`NameError: name 'CLK' is not defined`.

*Fix:* make the operands **closure** variables (`LOAD_DEREF` is not affected by
the globals swap) — build the program in a factory:

```python
def _make_sampler(clk_index, in_count, push, rising):
    @rp2.asm_pio(in_shiftdir=rp2.PIO.SHIFT_RIGHT, autopush=True,
                 push_thresh=push, fifo_join=rp2.PIO.JOIN_RX)
    def sampler():
        wrap_target()
        wait(0 if rising else 1, gpio, clk_index)   # hoist the constant out of the body
        ...
    return sampler
```

(Keep the two literal `wait` orderings in two `if` branches as now; only the
*names* need to become closure cells.) Default arguments
(`def sampler(clk=CLK_PIO_INDEX, n=IN_COUNT)`) also work, since `asm_pio` calls
`f()` with no arguments and defaults are bound at `def` time — but the factory
reads better and keeps `rising` out of the assembled body.

*Test:* add a stub `rp2`/`machine` harness that mimics the contract — clear
`f.__globals__`, install the mnemonics, call `f()` twice — and record the emitted
instruction words. That single harness catches C1 and lets you assert the real
instruction encodings (`0x2080|idx`, `0x2000|idx`, `0x4000|bits`) instead of
substring order.

**C2. `SHIFT_RIGHT` + `push_thresh=24` left-justifies the RP2040 samples; the
host header says right-justified.** `capture_rp2.py:147-158`, `boards.py:30-38`,
consumed by `vgacap/stream.py:39` `unpack_words()`. Full reasoning and both fixes
in the section above. Every RP2040 capture would decode to noise; the RP2350
path is correct.

### Important

**I3. Input pads are never initialised; on RP2350 they are isolated at reset.**
`capture_rp2.py:183` passes `in_base=machine.Pin(IN_BASE)` and the clock is read
with `wait gpio`, but nothing configures either pad.
`ports/rp2/rp2_pio.c` calls `pio_gpio_init()` only for `out`/`set`/`sideset`
pins, and for `jmp_pin` **only when the pad's `ISO` bit is set** (`:749-750`) —
a deliberate RP2350 workaround that the `in_base` path does not get, and that the
`wait gpio` clock pin cannot get because no `jmp_pin` is declared. RP2350 pads
come out of reset with `PADS_BANK0_GPIOx.ISO = 1`, so an untouched pad reads 0
and the capture silently records all-zero samples with no RXSTALL to warn you.
(RP2040 is fine: pads reset with `IE=1` and PIO sees the pad input regardless of
funcsel.) Note also that bare `machine.Pin(n)` with no mode does **not** touch
the hardware in the rp2 port.
*Fix:* before creating the state machine, `machine.Pin(CLK_GPIO, machine.Pin.IN)`
and `machine.Pin(g, machine.Pin.IN)` for `g in range(IN_BASE, IN_BASE+IN_COUNT)`.

**I1. The ping-pong does not survive its first overrun, and the overrun may not
even be counted.** `capture_rp2.py:232-248`.
The re-arm itself is right — deviation (3)'s premise checks out: chaining
re-triggers the partner but reloads neither `WRITE_ADDR` (it has advanced) nor
`TRANS_COUNT` (it has decremented to 0), and
`DMA.config(write=…, count=…, trigger=False)` writes exactly those two registers
through the non-trigger aliases and leaves `ctrl`/`read` alone (verified in
`rp2_dma.c:229-284`). The problem is the losing race:

1. `dma_a` completes → IRQ sets `full[0]`, chain triggers `dma_b`.
2. The main loop spends `BUF_BYTES` worth of USB time writing `bufs[0]`.
3. If `dma_b` completes during that write, its chain trigger fires at `dma_a`
   **while `dma_a` still has `TRANS_COUNT == 0`** — a null trigger.
4. Only *then* does the loop clear `full[0]` and re-arm `dma_a` (`:238,241`) —
   but nothing will ever trigger it again, because its one chain trigger was
   already consumed.

Outcome: the loop writes `bufs[1]`, re-arms `dma_b`, and then blocks forever in
`while not full[0]: machine.idle()` with both channels idle, the RX FIFO
overflowing and **`overruns[0]` still 0** — a silent hang, not a reported
overrun. (If a null trigger does propagate its chain on this silicon, the
failure mode is the opposite: a mutual null-trigger IRQ storm.) Either way the
detection the brief asked for — "a hard IRQ finds its buffer still full" — only
fires in the second case.
A related hazard: if the partner *does* re-trigger `dma_a` before step 4, the
re-arm at `:241` rewrites `WRITE_ADDR`/`TRANS_COUNT` of a running channel and
corrupts the destination mid-transfer.
*Fix:* after re-arming, detect the stall and restart deterministically, e.g.

```python
dmas[index].config(write=bufs[index], count=BUF_WORDS, trigger=False)
if not dmas[1 - index].active():      # partner already finished: chain was lost
    overruns[0] += 1
    dmas[index].active(1)             # re-trigger explicitly
```

and consider stopping the capture on the first overrun (emit the `TIME` chunk and
break) rather than continuing to emit a stream whose sample continuity is gone.
A third buffer, or checking `dmas[index].active()` before reconfiguring, would
remove the mid-transfer-rewrite window.

**I2. No `try/finally` around the SM/DMA lifetime.** `capture_rp2.py:176-261`.
The `try` starts at `:232`, after `rp2.DMA()` allocation (`:199-200`), `irq()`
registration and `sm.active(1)`. Any exception raised in setup — or a
`KeyboardInterrupt` arriving between `:199` and `:232`, which is exactly the
window the host uses to stop a run — leaves the state machine running, two DMA
channels claimed and two IRQ handlers registered. `rp2.DMA()` then raises
"no free DMA channels" on the next attempt and the board needs a soft reset
between captures. Wrap the whole body from `dma_a = rp2.DMA()` in
`try: … finally: sm.active(0); dma_a.close(); dma_b.close()`.

### Minor (13)

1. `capture_rp2.py:253-255` — `DMA.active(0)` is `dma_channel_abort()` on a
   channel whose `chain_to` still points at its partner. pico-sdk warns that on
   RP2350 (errata **RP2350-E5**) the enable bit of the aborted channel *and its
   chain partners* must be cleared first to prevent re-triggering, and on RP2040
   an abort can raise a spurious completion IRQ. Here that spurious IRQ inflates
   `overruns[0]`, which is read at `:260-261` *after* the aborts. Clear
   `chain_to`/`EN` (or disable the IRQs) before aborting, and snapshot the
   overrun count before shutdown.
2. `capture_rp2.py:226-227` — the SM is started before the DMA is armed. Arm
   `dma_a` first, then `sm.active(1)`, so the first samples cannot stall the RX
   FIFO during the MicroPython call overhead between the two lines.
3. `capture.py:20,55` — `DEFAULT_SYSCLK_HZ = 133_000_000` is applied to
   `RP2350_DBV3` too; the rp2 port boots RP2350 at 150 MHz. Since the value is
   only informational, have the board report `machine.freq()` in the closing
   `TIME` message instead of the host guessing.
4. `capture_rp2.py:236,250` — a `KeyboardInterrupt` inside `_write_all` emits a
   truncated `RAW ` chunk and then still appends the closing `TIME` chunk, which
   desyncs the length-driven reader Task 4 will build. Track "a chunk is
   in flight" and either finish it or skip the trailer.
5. `mp/throughput.py:49` — `out.write(data[pos:])` copies the entire block on the
   *first* pass (`pos == 0`), i.e. an extra 32 KB allocation per write on a board
   that already allocates `source[phase:phase+n]`. `capture_rp2.py:159` gets this
   right (`data[pos:] if pos else data`); use the same form here. It inflates
   heap churn on exactly the path whose speed is being measured.
6. `throughput.py:33` — `_DOUBLE` is dead code.
7. `throughput.py:115` — the clock starts before the generator is first advanced,
   so the script upload and the board's compile time are charged to the transfer.
   Start timing after the `OK` ack (e.g. yield a zero-length sentinel, or expose
   the ack time from `exec_stream`).
8. `capture_rp2.py:245` — `sent += 8 + 18 + 7` hard-codes the `TIME` chunk size
   including `len(b"overrun")`. Return the byte count from `write_time_chunk()`.
9. `capture_rp2.py` — no `out.flush()` before returning, and no guard on the
   MicroPython feature set (`rp2.DMA` needs ≥ 1.22, `PIO.gpio_base` ≥ 1.24). A
   one-line `hasattr` check with a `TIME` chunk carrying the reason would fail
   far more legibly than an `AttributeError` traceback on stderr.
10. `test_capture_rp2_pio.py` — the PIO assertions are substring/ordering checks

    the docstring deliberately avoids the literals shows how brittle that is. The
    stub-`rp2` harness proposed under C1 replaces all of them with real
    assertions on emitted instruction words and on the decoded sample layout.
11. `test_capture_rp2_pio.py:418-453` — `test_script_inlines_the_same_address_…`

    `test_rising_edge_program_…` slices from the first `in_(pins,` occurrence, so

### Deviations — verdicts

1. **Pattern minus `0x04`** — accepted, see Task 2 above. On the follow-on
   question: the framing *does* support length-driven reads. Every chunk is
   `4-byte tag + u32 payload length + payload`, `write_raw_chunk`/`write_time_chunk`
   are the only writers, and nothing else is printed, so a host that reads 8 bytes,
   then exactly `length` bytes, then the next header, never has to scan for a
   terminator. Two caveats for Task 4: minor #4 above (an interrupted chunk breaks
   the invariant), and a silently dropped USB CDC write on the board would desync
   the reader with no resync marker — validating the tag against the four known
   tags and failing loudly is cheap insurance.
2. **`clk_gpio - gpio_base`** — **verified correct**, and it is not merely
   defensible, it is required. `PIOASMEmit.wait()` emits
   `0x2000 | polarity<<7 | src<<5 | index` with the index *verbatim and unmasked*,
   and the RP2350 PIO adds `GPIOBASE` to the WAIT GPIO index (pico-sdk #2141:
   with `gpio_offset` 16 the encodings are `0x2002` for GPIO 18 and `0x2012` for
   GPIO 34). Passing an absolute 33 would not just be off by 16, it would spill
   into the `src` field and assemble a different instruction. On RP2040
   `GPIO_BASE == 0`, so the expression is identical to the brief's. Both profiles
   land on index 0 here, which is also why the accompanying test is weak evidence —
   it would pass for `CLK_GPIO` too. A `pio=1, gpio_base=16, clk_gpio=20` case
   would pin it properly.
   Related and also correct: `in_base=machine.Pin(33)` *is* the right thing to
   pass. MicroPython hands the absolute pin straight to
   `sm_config_set_in_pin_base()`, which stores `base & 31` plus a `pinhi` shadow,
   and `pio_sm_set_config()` flips bit 4 when `GPIOBASE == 16` (`33 & 31 = 1`,
   `1 ^ 16 = 17 = 33 - 16`) — and it returns `PICO_ERROR_BAD_ALIGNMENT` if the
   base is out of the window, which is why `gpio_base()` must precede the
   `StateMachine` as the script does.
3. **DMA re-arm** — premise correct, implementation racy: see **I1**.
4. **`ttcap/mp/__init__.py` holding `load()`/`with_cfg()`** — fine, matches the
   dispatch, and the loader's bare-name check is a nice touch.
